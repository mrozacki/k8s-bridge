# demo-console — single-screen demo control surface

A presenter console for showing k8s-bridge end to end without switching
windows: one browser tab with a **live terminal you can type into** on one
side, and **live cluster/bridge state** (Grafana, or a bridge-top-style
status strip) on the other, plus a click-to-copy cheat sheet of the
`experiments/DEMO.md` script.

## Does it answer "can I type terminal commands directly in the demo UI"?

**Yes.** The terminal pane is [ttyd](https://github.com/tsl0922/ttyd) — a
small Go binary that wraps a real shell and streams it into the browser
over a websocket, embedded here in an `<iframe>`. Anything you type into
that pane executes for real, in the exact shell `serve.sh` started (your
own `$SHELL` by default), against whatever cluster your `kubectl` context
points at. It is not a simulation or a read-only view — click a command in
the cheat sheet to copy it, then paste it straight into the terminal pane
and press enter, without ever leaving the page.

## What this is

```
tools/demo-console/
├── index.html          the one page — layout: cheat sheet | terminal + dashboard
├── app.js              client logic: renders cheat sheet, wires up the
│                        terminal iframe, polls status or embeds Grafana
├── cheatsheet.js        the numbered steps from experiments/DEMO.md, as data
├── style.css            layout/theme (dark, single dependency-free stylesheet)
├── config.js             generated by serve.sh at launch (ports/URLs);
│                        checked-in version is an empty fallback
├── static-server.js      dependency-free Node static file server for the page
├── status-api.js         tiny Node HTTP wrapper around status-snapshot.sh
├── status-snapshot.sh     kubectl-derived JSON snapshot (reuses ../bridge-top.sh's queries)
└── serve.sh               launcher: starts ttyd + status-api + static server
```

No build step, no npm install, no framework — plain HTML/CSS/JS served by
Node's built-in `http` module, plus one small Bash script reusing the same
`kubectl get` queries as `tools/bridge-top.sh`.

## Prerequisites

- `kubectl` on PATH, pointed at a running playground cluster (see
  `experiments/DEMO.md` §1) — the status strip and terminal both act
  against this context. The console itself does not create or need a
  cluster to **load**; the status strip and any `kubectl`/`sbatch` commands
  you type will simply report "unreachable" until one exists.
- `node` on PATH (any reasonably recent version; only core modules are
  used — `http`, `fs`, `path`, `child_process`).
- **`ttyd`** — the web terminal. Install on macOS:
  ```bash
  brew install ttyd
  ```
  `serve.sh` checks for it and prints this exact instruction if it's
  missing; it will not silently degrade the terminal panel (a fake
  terminal would be worse than an honest error).
- Optional: a running Grafana instance with the dashboards from
  `dashboards/researcher-dashboards.json` imported, if you want to embed
  Grafana instead of the built-in status strip.

## Launch

```bash
cd tools/demo-console
./serve.sh
```

This starts three localhost-only processes and prints **one URL** to open:

```
http://127.0.0.1:8842/
```

Open that URL, put it on the projector, and present from it — no window
switching for the rest of the demo.

### Optional environment variables

| Variable | Default | Effect |
|---|---|---|
| `GRAFANA_URL` | (unset) | If set, the dashboard pane embeds this URL in an iframe instead of the status strip, e.g. `GRAFANA_URL=http://localhost:3000/d/wm-researchers ./serve.sh` |
| `TTYD_PORT` | `7681` | Port ttyd listens on |
| `STATUS_PORT` | `8843` | Port the status API listens on |
| `PAGE_PORT` | `8842` | Port the page itself is served on — this is the one URL you open |
| `DEMO_SHELL` | `$SHELL` (fallback `/bin/zsh`) | Shell ttyd wraps |

You can also override the terminal/status/Grafana URLs per-load via query
params on the page itself (`?ttyd=...&statusApi=...&grafana=...`) without
restarting `serve.sh` — useful if you're pointing the console at services
running somewhere other than localhost defaults.

Stop everything with `Ctrl+C` in the terminal running `serve.sh` — it kills
all three child processes on exit.

## How the single-screen workflow works

1. **Left panel — cheat sheet.** The numbered steps from
   `experiments/DEMO.md`, collapsed by default; click a step to expand it,
   click **Copy** next to any command to copy just that line, or
   **Copy all lines** to copy the whole step's block.
2. **Right panel, top — terminal.** An embedded ttyd session. Paste (or
   type from scratch) into it; it is a real shell with your real
   `kubectl`/`gcloud`/`sbatch` on PATH, scoped to whatever the operator's
   machine has configured.
3. **Right panel, bottom — dashboard.** Either a Grafana iframe (if
   `GRAFANA_URL` is set) or a live-polling status strip modeled on
   `tools/bridge-top.sh` — nodes, ClusterQueues, Workloads, bridge
   JobSets, `squeue`, `sinfo` — refreshed every 5 seconds from the same
   `kubectl` queries, rendered as text panels instead of a scrolling
   terminal UI.

The presenter never leaves this one tab: narrate from the cheat sheet,
click-copy a command, paste it into the terminal, watch the result appear
in the dashboard panel below it.

## Security caveats — read before using this anywhere but a laptop demo

**This tool exposes a real, writable shell over HTTP.** That is the entire
point (typed commands must run somewhere), but it means:

- `serve.sh` binds ttyd, the status API, and the static page server to
  `127.0.0.1` **only**. Do not change this to `0.0.0.0`, do not
  port-forward these ports to a public interface, and do not tunnel them
  (e.g. `ngrok`) to share the demo remotely — anyone who can reach the
  ttyd port gets a shell with your privileges and your `kubectl`/`gcloud`
  credentials.
- ttyd is started with `-W` (client input enabled / writable). This is
  required for the "type commands directly" feature — a read-only ttyd
  would defeat the purpose — but it is precisely what makes exposure
  dangerous. There is no authentication in front of it by default; ttyd
  supports `-c user:pass` for basic auth if you ever need to loosen the
  localhost-only rule, but the recommended posture for this tool is
  **localhost-only, no exception**.
- The status API (`status-api.js`) shells out to `kubectl`/`squeue`/
  `sinfo` via a fixed script (`status-snapshot.sh`) with no user-supplied
  input — it does not accept parameters that reach a shell, so it does not
  add its own command-injection surface beyond what `bridge-top.sh`
  already has (same queries, same trust model: whoever can reach this port
  can read your cluster's Workload/queue state).
- Treat this exactly like running `kubectl proxy` or a local Jupyter
  notebook without a token: fine on your own machine for your own demo,
  never fine to expose beyond `127.0.0.1`.

## What was validated locally vs. what needs a live cluster

**Update (2026-07-06, this session): `kind` + `ttyd` WERE available this
time** (`brew install kind ttyd`, both succeeded; Docker Desktop was
already running). This session went well beyond the previous static-only
pass — it stood up a real (free, local) `kind` cluster, ran `serve.sh`
against it end to end, and drove the actual rendered page in a real browser
via automation. Everything below marked **(2026-07-06 live)** is new
evidence from that run; the cluster was torn down afterward
(`kind delete cluster --name demo-console-test`, confirmed empty via
`kind get clusters` and `docker ps -a`) — zero persistent cost, this never
touched GCP.

**Validated live against a real (if minimal) cluster (2026-07-06):**

- `kind create cluster` stood up a real local Kubernetes control plane in
  under a minute; `serve.sh` started all three processes
  (ttyd, `status-api.js`, `static-server.js`) against it without errors.
- **ttyd actually serves a working terminal**: `curl` confirmed the ttyd
  HTML page (`<title>ttyd - Terminal</title>`) and a clean WebSocket
  handshake (`HTTP/1.1 101 Switching Protocols` on `/ws`). Driving a real
  Chrome tab against `http://127.0.0.1:8842/`, the embedded terminal iframe
  rendered a live shell prompt, and **typing `kubectl get nodes` directly
  into the browser-embedded terminal executed for real** and returned the
  actual kind cluster's node — the tool's headline claim ("type commands
  directly, no simulation") is now proven, not just asserted.
- **The status strip rendered real, non-empty data for the first time**:
  `context: kind-demo-console-test` and
  `demo-console-test-control-plane Ready` appeared in both the raw
  `curl http://127.0.0.1:8843/status` JSON and the rendered page: the
  previously-untested "real node data" path now has live evidence. The
  empty-state sections (ClusterQueues/Workloads/JobSets/squeue/sinfo — none
  of that is installed on a bare `kind` cluster) rendered their documented
  graceful placeholders (`(none)`, `(login pod unavailable or empty)`)
  exactly as designed, alongside the real node data — confirming the
  degrade-gracefully behavior holds even when *some* fields are real and
  others are absent, not just the all-or-nothing states tested previously.
- **Found and fixed a real, previously-undiscovered bug**: the cheat-sheet
  panel rendered **zero** steps in the live browser, despite `cheatsheet.js`
  loading with no syntax error. Root cause: `cheatsheet.js` declares
  `const DEMO_STEPS = [...]` and is loaded as a plain classic
  `<script src="cheatsheet.js">` (not a module) — a top-level `const` in
  that context is scoped to the script itself and never becomes a `window`
  property, so `app.js`'s `window.DEMO_STEPS` read was always `undefined`.
  This bug existed since the tool's first commit; the static
  `node --check`/`bash -n` pass never caught it because both files are
  independently syntactically valid — it only shows up by actually loading
  the page in a browser and inspecting the DOM. Fixed in `cheatsheet.js`
  with an explicit `window.DEMO_STEPS = DEMO_STEPS;` assignment. Re-tested
  live after the fix: all 17 steps render, expand/collapse on click, and
  the per-command "Copy" button shows the "Copied" confirmation state
  correctly (clipboard write succeeded silently, no permission prompt, on
  Chrome/macOS/`http://127.0.0.1`).
- `cheatsheet.js`'s step count and titles were also confirmed, live, to
  match `experiments/DEMO.md`'s current 18-section numbering exactly
  (steps 1-17 correspond to DEMO.md sections 1-17; section 0 "Prereqs" and
  18 "Troubleshooting" are not standalone cheat-sheet steps by design).

**Validated without a cluster** (static checks, still useful independent of
the live pass above):

- `node --check` passes on every `.js` file (`app.js`, `cheatsheet.js`,
  `config.js`, `static-server.js`, `status-api.js`) — no syntax errors.
- `bash -n` passes on `serve.sh` and `status-snapshot.sh`.
- `index.html` parses cleanly (no unclosed tags / malformed markup) via
  Python's `html.parser`.
- `static-server.js` serves `index.html`, `app.js`, `cheatsheet.js`,
  `style.css`, and `config.js` with correct MIME types and 200 status
  (verified with `curl`); it blocks path traversal (`../../../etc/passwd`
  falls back to `index.html`, does not leak the real file) and returns a
  safe SPA-style fallback for unknown paths.
- `status-api.js` runs `status-snapshot.sh` against a `kubectl` with no
  reachable cluster and degrades gracefully — returns a well-formed JSON
  document with empty arrays and `"bridgeReady": "unknown"` rather than
  crashing or hanging; confirmed via `curl http://127.0.0.1:8843/status`.
- `serve.sh`'s ttyd presence check was exercised (in an earlier session,
  before `ttyd` was installed) on a machine without `ttyd`: it correctly
  refused to proceed and printed the `brew install ttyd` instruction
  instead of failing opaquely or silently skipping the terminal panel.
- `cheatsheet.js` commands were spot-checked against `experiments/DEMO.md`
  for exact text match, including the one command with nested single/double
  quotes (the Ray pinned-worker `kubectl run --overrides=...`), and the two
  new steps added this session (control-plane/ADR-0011, per-partition
  queues).

**Still not validated (needs a real Slurm+Kueue+bridge stack — GKE, per
`docs/adr/0003-gke-first-playground.md`'s reasoning that Slinky's
dynamic-node registration needs a real cluster network, not `kind`):**

- The status strip rendering real ClusterQueue/Workload/JobSet/squeue/sinfo
  data — this session's `kind` cluster had none of those installed (no
  Slurm, no Kueue, no bridge), so only the "genuinely absent" path was
  exercised for those fields, not the "present with real data" path. A
  bare `kind` cluster cannot close this gap either (see the "Runs on GKE,
  not kind" note at the top of `experiments/DEMO.md`) — this needs the
  next live GKE session.
- Grafana iframe embedding against a real Grafana instance — in
  particular, Grafana's default `X-Frame-Options`/CSP headers **block**
  iframe embedding unless the Grafana server's config explicitly sets
  `allow_embedding = true` under `[security]` (`grafana.ini`) and, for
  anonymous/no-login viewing in an iframe, typically
  `[auth.anonymous] enabled = true`. This is a known constraint, not a bug
  in this tool — if the Grafana panel appears blank, check those two
  settings on the Grafana server first (documented in the dashboard-mode
  header text in the UI, and worth calling out during a demo dry run
  before relying on it live).
- The presenter's actual OS/browser combination for the live event (this
  session validated Chrome on macOS via automation; a manual dry run on
  the actual presenting machine is still worthwhile before a real demo).

## Design notes / alternatives considered

- **ttyd vs. gotty vs. a custom xterm.js + node-pty server:** ttyd was
  chosen because it is a single static binary (`brew install ttyd`), has
  no runtime dependencies, and its `-W` flag directly satisfies "type
  commands directly" (bidirectional, not view-only). `gotty` (the Go
  project ttyd was inspired by) is effectively unmaintained upstream;
  building a custom `xterm.js` + `node-pty` server was rejected as
  unnecessary weight for this use case — it would require an npm
  dependency tree and a native build step (`node-pty` compiles a native
  addon), which conflicts with the "dependency-light" requirement. ttyd
  gets the same outcome from a single `brew install`.
- **iframe embedding for both terminal and Grafana:** kept both panels as
  plain `<iframe>` elements rather than proxying/rewriting either — this
  keeps `app.js` tiny and avoids reimplementing terminal rendering or
  Grafana's panel JS. The tradeoff is the Grafana X-Frame-Options
  constraint noted above, which is inherent to iframe embedding of any
  third-party app and not specific to this tool.
- **Status strip as a fallback, not a requirement:** the page works fully
  (terminal + cheat sheet) even with zero Grafana and zero live cluster —
  it just shows an honest "unreachable" state rather than failing to load.
  This matches `tools/bridge-top.sh`'s own philosophy of graceful
  degradation, and reuses its exact `kubectl` query shapes so the two
  tools never show contradictory information.
- **No bundler/framework:** given the audience (a presenter showing
  colleagues, run from a laptop, GitHub-published as prototype code), a
  build step would add failure modes (version drift, `node_modules`
  bloat) for no real benefit at this scale — three static files and two
  ~100-line Node scripts are easier to read end to end than a bundled
  output.
